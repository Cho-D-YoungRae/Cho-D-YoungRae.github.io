# GitHub 이슈 라벨·템플릿 개인 블로그용 재설계

- 작성일: 2026-08-04
- 대상 저장소: `Cho-D-YoungRae/Cho-D-YoungRae.github.io` (퍼블릭, 1인 운영)

## 배경

저장소가 GitHub 기본 라벨 9개를 그대로 쓰고 있다. 이 중 `good first issue`,
`help wanted`, `duplicate`, `invalid` 같은 오픈소스 협업용 라벨은 1인 기술
블로그에서 쓸 일이 없다. 반대로 블로그 운영에 실제로 필요한 "쓰고 싶은 글
주제 등록"에 해당하는 라벨은 없다.

이슈 템플릿도 없어서 새 이슈를 만들 때마다 빈 화면에서 시작하고 라벨을 손으로
붙여야 한다.

## 목표

이슈로 관리할 대상은 세 가지다.

1. 글 주제·집필 관리 (이슈 1개 = 게시글 1편)
2. 블로그 기능·디자인 개선
3. 버그·오류 수정

## 비목표 (명시적으로 하지 않는 것)

- **집필 진행 상태 추적 안 함.** `status: 초안` 같은 상태 라벨을 만들지
  않는다. 열림 = 할 일, 닫힘 = 완료로만 구분한다. GitHub Projects 보드도
  쓰지 않는다.
- **분류축을 늘리지 않음.** 우선순위(`priority: high`), 기술 분야(`AI`,
  `backend`), 작업 분량(`size: M`) 라벨을 만들지 않는다. 게시글이 3편인
  시점에 분류축을 늘리면 관리 비용만 늘고 쓰이지 않는다. 필요해지면 그때
  추가한다.
- **라벨 정의를 코드로 관리하지 않음.** `.github/labels.yml` + 동기화
  워크플로를 두지 않는다. 라벨 5개짜리 저장소에는 워크플로 유지비가 더 크고,
  각 라벨명은 이슈 템플릿 파일의 `labels:` 필드에 이미 기록된다.
- **학습·리서치 메모는 이슈로 관리하지 않음.**

## 설계

### 1. 라벨 세트 (9개 → 5개)

블로그가 한국어(`lang: ko`)이고 커밋 메시지도 한글이므로 라벨명도 한글로 한다.

| 라벨 | 색상 | 설명 | 용도 |
|---|---|---|---|
| `글감` | `#0E8A16` | 쓰고 싶은 글 주제 | 이슈 1개 = 게시글 1편 |
| `글 수정` | `#FBCA04` | 발행한 글의 보완·정정 | 오타, 정보 갱신, 내용 추가 |
| `기능` | `#1D76DB` | 블로그 기능·디자인 개선 | 테마, 컴포넌트, 검색, 댓글 |
| `버그` | `#D73A4A` | 오류·깨짐 수정 | 빌드 실패, 링크 깨짐, 레이아웃 |
| `보류` | `#CFD3D7` | 당장은 하지 않기로 함 | 닫을 때 이유 표시 |

### 2. 기존 라벨 처리

현재 이슈가 0개라 삭제와 이름 변경의 실질 차이는 없지만, 의미가 이어지는
라벨은 `gh label edit`으로 이름만 바꿔 참조가 끊기지 않게 한다.

**이름 변경 3개**

| 기존 | 변경 후 | 색상 변경 |
|---|---|---|
| `bug` | `버그` | `#D73A4A` 유지 |
| `enhancement` | `기능` | `#a2eeef` → `#1D76DB` |
| `wontfix` | `보류` | `#ffffff` → `#CFD3D7` |

**신규 생성 2개**: `글감`, `글 수정`

**삭제 6개**: `documentation`, `duplicate`, `good first issue`,
`help wanted`, `invalid`, `question`

`question`을 지우는 이유는 저장소에 Discussions가 이미 켜져 있고(Giscus 댓글
연동), 독자 질문은 그쪽으로 가는 것이 맞기 때문이다.

`documentation`은 README·CLAUDE.md 갱신 같은 작업을 가리키는데, 그 정도는
`기능`에 포함해도 충분하다.

### 3. 이슈 템플릿

`.github/ISSUE_TEMPLATE/` 아래 GitHub Issue Forms(YAML) 형식으로 만든다.
템플릿을 고르면 해당 라벨이 자동 부착되므로 매번 손으로 붙일 필요가 없다.

각 템플릿은 `name`, `description`, `title`(접두어), `labels`, `body`를 갖는다.

**주의: `name`과 각 필드의 `label`은 최소 3자여야 한다.** GitHub이 한글도 문자
단위로 세기 때문에 `글감`, `버그`, `환경` 같은 2자 값은
`Name is too short (minimum is 3 characters)` 오류로 거부되고 해당 템플릿이
목록에 뜨지 않는다. 이 때문에 템플릿 이름을 `글감 등록`, `버그 기록`으로,
필드 이름을 `사용 환경`으로 두었다. `labels:`에 들어가는 라벨명은 이 제약과
무관하므로 `글감` 그대로 쓴다.

#### `post-idea.yml` — 글감 등록

- `labels: [글감]`, `title: "[글감] "`
- 필드
  - `textarea` **다룰 내용** (필수) — 무엇을 쓸지
  - `input` **예상 태그** — 게시글 frontmatter의 `tags`에 들어갈 값
  - `textarea` **참고 자료** — 링크, 읽을거리
  - `textarea` **쓰려는 이유·목표** — 이 글로 무엇을 남기고 싶은지

#### `post-edit.yml` — 발행글 수정

- `labels: [글 수정]`, `title: "[글 수정] "`
- 필드
  - `input` **대상 글** (필수) — 블로그 URL 또는 `src/content/posts/` 경로
  - `textarea` **고칠 내용** (필수)

#### `improvement.yml` — 기능·디자인 개선

- `labels: [기능]`, `title: "[기능] "`
- 필드
  - `textarea` **지금 상태**
  - `textarea` **바라는 상태** (필수)
  - `textarea` **참고 사례** — 참고할 사이트·구현

#### `bug.yml` — 버그

- `labels: [버그]`, `title: "[버그] "`
- 필드
  - `input` **발생 위치** — 페이지 URL 또는 명령
  - `textarea` **재현 방법** (필수)
  - `textarea` **기대 동작**
  - `input` **환경** — 브라우저, 기기

#### `config.yml`

- `blank_issues_enabled: true` — 위 네 갈래에 안 맞는 메모를 빈 이슈로 남길
  수 있게 열어둔다.
- `contact_links`에 Discussions 링크를 넣어 "글에 대한 질문·의견"은 그쪽으로
  안내한다. URL은
  `https://github.com/Cho-D-YoungRae/Cho-D-YoungRae.github.io/discussions`.

## 검증 방법

1. `gh label list`로 최종 라벨이 정확히 5개이고 이름·색상·설명이 표의 값과
   일치하는지 확인한다.
2. `.github/ISSUE_TEMPLATE/*.yml`이 GitHub의 issue form 스키마를 만족하는지
   확인한다. 스키마 위반이 있으면 GitHub이 템플릿 목록에서 해당 항목을 숨기고
   저장소 이슈 탭에 오류를 표시하므로, 푸시 후 실제 "New issue" 화면에서 네
   템플릿이 모두 보이는지 눈으로 확인한다.
3. 템플릿 하나로 실제 이슈를 열어 라벨이 자동 부착되는지 확인한 뒤 닫는다.

## 참고

- 라벨 변경은 GitHub 원격 상태를 직접 바꾸는 작업이라 되돌리려면 다시 CLI를
  실행해야 한다. 삭제 대상 6개는 현재 어떤 이슈에도 붙어 있지 않다(이슈 0개).
